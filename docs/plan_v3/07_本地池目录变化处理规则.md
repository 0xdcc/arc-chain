# 本地池目录变化处理规则（四个主脑都必须知道）

计划ID：`ARC-4B-v3.1-20260911-13817f4`。用户在2026-09-11补充：本地`dex-sniper-engine-modular`后续会增加V3/V4池，其他代码预期不变，不要求本地与GitHub的整目录始终一致。

**结论：这是允许的正常数据变化，不是要求用户停止维护Robinhood的冻结令。只冻结“本次选用的代码”，不冻结原项目的全部目录。**

## 1. 三份东西必须分开

| 层次 | 如何处理 | 是否影响Arc施工 |
|---|---|---|
| 复用代码基线 | 本次已核对GitHub `13817f4e027375dd59cc7a202ae641c068525f53`；记录选用文件、依赖、测试和配置的哈希 | 只在这些逻辑/契约发生变化时定向复核 |
| 本地Robinhood池目录/数据快照 | 允许池条目增加、删除、标签/数量/采样数据变化；保存来源和as-of，不要求与GitHub数量/字节相同 | 单纯池数据变化不阻断Arc代码开发，不反复重做T01–T04 |
| Arc自己的主网注册表 | 由Arc实际网络身份、合约、部署和观测证明建立 | 从不由Robinhood池地址改chainId生成；与Robinhood持续维护独立 |

新增Robinhood池不会直接给Arc增加可交易场所。可复用的是池发现/元数据核验/状态读取/图与报价代码；链特定Factory、Manager、Router、Token、PoolId、部署块和链上历史必须分别注册。

## 2. 允许差异的判定流程（M1处理，用户不审Diff）

1. 先确认真实本地项目路径、Git HEAD与状态。**HEAD不同、工作树非干净、池数不同，都不是单独的失败条件。**不reset/clean、不stash掉用户变更、不强制pull或要求先push。
2. 对实际选用的复用代码及其导入依赖、相关配置/测试/构建文件计算内容摘要，与固定代码来源比对。使用本地已有Git对象或获准的只读下载获得基线；不要为了读取源改变正在运行的Robinhood工作树。
3. 单独列出池数据差异。默认候选仅为已知精确路径`data/v3_pools_live_catalog.json`与`data/v4_pools_live_catalog.json`；**不得写成整个data/**豁免**。其他文件先按内容、schema和消费者用途分类。JSON也可能是权限/目标合约/部署配置，不能只看扩展名。
4. 若选用代码及其依赖未变化，仅目录数据变化，记`DATA_ONLY_DIFFERENCE`、本地实际HEAD、文件哈希和统计，然后继续。不要要求用户确认每次加池，不重跑与该数据无关的全部验收。
5. 若代码/公共类型/费用算法/资格规则/安全配置变化，记`CODE_OR_POLICY_DIFFERENCE`并列影响任务。默认仍使用已冻结代码，在Arc独立工作区继续不受影响任务；确需采用新代码时由M1安排局部差分、M4复核。不是一看到dirty就全局停机。
6. 未知数据格式、内容畸形、文件正在写入，记`DATA_SNAPSHOT_UNAVAILABLE`或`UNCLASSIFIED`。只暂停该可选数据导入/依赖它的任务。允许继续使用固定来源测试fixture或Arc合成fixture；不能把坏数据默认为空表。

**“改源码内的池地址数组”“更换Router/Hook/协议参数”“移除某个安全检查”不属于默认池数据快路径。**数据本身也必须通过消费者验证；允许它与GitHub不同，不等于自动授予交易资格。

## 3. 本地文件怎样参与复用

默认选用固定Git代码对象。若本地选用代码与固定文件摘要一致，可以从本地一致性快照复制来节省下载，不必重新克隆一个大仓库。记录实际来源路径、源blob/sha256、目标sha256与代码锁。

如果本地代码确实更好但与固定来源不同，M1给这组补丁单独记版本和影响范围。不能四个主脑分别从变化中的本地目录复制不同版本；不能让Arc运行时import、软链接或共享可变venv到Robinhood目录。

池数据如果不用于Arc开发，则只登记“本地允许差异，未导入”，**不要求读取巨量缓存或运行中的账本**。确需用作测试时，按精确文件保存只读、一致、脱敏快照；不要求中断源服务或锁住用户的维护程序。文件写入竞争时采用有限次数重试，仍不一致就仅跳过这个可选快照。

不得给整个目录做一个总哈希当成代码版本。可记录：

```text
code_reference_sha       = 固定13817f4…
selected_code_digest     = 选用代码/依赖/配置/测试清单摘要
local_git_head          = 现场实际值，允许不同
local_catalog_snapshot  = 单独快照ID/哈希，或未使用
arc_catalog_generation  = Arc自身注册表版本
arc_candidate_sha       = 本次实际被测的Arc提交
```

## 4. 测试数量和样本不能反过来绑住用户

上游`tests/test_v4_pipeline_integration.py`里的137个V3、至少200个V4、5000条回路等，是当时特定Robinhood样本的断言，不是Arc目标，也不是用户本地永远不能加池的约束。[R5]

- 原样上游回归：使用对应固定代码版本的固定fixture，保留原测试义务和原断言；不要用变化后的本地目录制造假失败。
- Arc通用回归：验证schema、真实身份、重复条目处理、能力支持、费用、精度与状态一致性；用已标注的Arc测试fixture。
- 测试本地新目录：记录实际样本数量和性能影响；更新样本预期需要说明依据，不通过删断言/忽略失败来掩盖问题。

新目录会改变Robinhood回路数、CPU/RPC/内存负载，不能承诺性能完全不变；但这不改变Arc的四主脑分工和独立代码复用方案。

## 5. 四个主脑分别负责什么

**M1：**执行差异分类、维护代码锁和数据快照记录，不向用户反复索要“整库干净”；只有代码实质变化才安排对应复核。

**M2：**不读取Robinhood目录当Arc生产源；沿用核验方法，自己发现Arc池。后续Arc注册表更新也用版本化完整候选快照发布，消费者不读取半份更新。

**M3：**报价/历史数据绑定`code_digest + catalog_generation + state_ref`；原样上游回归用固定fixture。不能因为本地池数增多就宣称Arc机会变多。

**M4：**新增“只改池目录可以继续”“代码变化不能伪装数据变化”“混合代码/数据变化被正确分类”“未知/半写文件不被默默信任”反证。纯数据差异不要求重新审完整系统；必须采纳的代码变化则按实际影响复审。

## 6. 与旧冻结规则的关系

本条是用户明确补充的正常数据变化政策。包内“固定来源SHA”“不各窗追main”均指固定代码选择，**不指本地整仓HEAD、目录字节或池数必须与GitHub一样**。需要保留安全边界，但不得用版本管理手续阻碍无关工程进度。
